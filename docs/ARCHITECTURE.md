# 설계 문서

## 왜 이런 모양인가

목표는 "git 처럼 제안하고 리뷰하고 병합하되, 대상은 코드가 아니라 파일"입니다.
그래서 git 의 개념 중 **쓸모 있는 것만** 가져오고 나머지는 뺐습니다.

| git 개념 | ListUp | 이유 |
| --- | --- | --- |
| commit | snapshot | 그대로 필요. 다만 "그 시점의 전체 파일 목록"으로 단순화 |
| branch | 없음 | 파일 공유에는 장기 분기가 거의 안 생긴다. 개념 하나를 줄임 |
| pull request | proposal(변경 제안) | 핵심. 열람 권한만 있어도 기여할 수 있는 통로 |
| 3-way merge | 하지 않음 | 대상이 대부분 바이너리. 자동 병합이 의미가 없고 위험함 |
| clone / push | 없음 | 서버가 유일한 원본. 모바일에서 로컬 사본을 관리시키지 않음 |

## 데이터 모델

```
users ──┬─< repo_members >─┬── repos ──< snapshots ──< snapshot_entries >── blobs
        │                  ├── repo_blobs (어느 저장소에 올렸는지) ────────────┘
        │                  │              (head)              │
        │                  ├── invites                        │
        │                  └── proposals ──< proposal_changes ┘
        └─────────────────────< proposal_comments
```

### 스냅샷 = 그 시점의 전체 파일 목록

파일이 바뀔 때마다 새 `snapshots` 행과, 그 시점의 **모든** 파일에 대한 `snapshot_entries`
행을 만듭니다. `repos.head_snapshot_id` 가 현재 상태를 가리킵니다.

델타가 아니라 전체 목록을 매번 쓰는 이유:

- 어떤 시점의 파일 목록을 읽는 것이 인덱스 조회 한 번으로 끝납니다. 히스토리를 거슬러 올라가며
  델타를 적용할 필요가 없습니다.
- 실제 파일 바이트는 `blobs` 에 콘텐츠 주소로 한 번만 저장되므로, 목록이 반복돼도 저장 공간은
  경로 문자열만큼만 늘어납니다.
- 파일 수천 개 규모(`MAX_FILES_PER_REPO = 5000`)에서는 이 단순함이 이깁니다. 그 이상으로
  커지면 델타 저장으로 바꿔야 합니다.

### 콘텐츠 주소 저장소

업로드된 바이트는 SHA-256 해시로 주소가 정해지고 `<blobDir>/ab/cd/<hash>` 에 놓입니다.

- 같은 파일을 여러 저장소가 가지고 있어도 실제 바이트는 하나입니다.
- 같은 파일을 다시 올리면 해시가 같으므로 **새 스냅샷을 만들지 않습니다**(`unchanged: true`).
- 다운로드 응답의 `ETag` 는 blob 해시입니다. 다만 다운로드 URL 은 해시가 아니라 **경로** 기준이라,
  현재 파일을 받는 요청은 `no-cache`(매번 `If-None-Match` 로 확인)이고, `snapshot` 을 지정한 요청과
  제안 파일만 `immutable` 로 캐시합니다.
- 업로드는 임시 파일에 받아 해시를 구한 뒤 `flush` 하고 최종 경로로 `rename` 합니다. 중간에 끊긴
  업로드가 정상 파일로 남지 않고, 기동 시 오래된 임시 파일을 정리합니다.
- blob 은 전역으로 공유되지만 **어느 저장소에 올렸는지**는 `repo_blobs` 에 남깁니다. 제안에는 그
  저장소에 올렸거나 그 저장소 이력에 있는 blob 만 담을 수 있어, 해시만 알고 있는 사람이 남의
  파일을 제안 경유로 읽을 수 없습니다.

빈 디렉터리는 저장하지 않습니다. 폴더 목록은 조회 시점에 경로 접두사로 만들어 냅니다.

## 권한

`viewer < editor < owner` 3단계이고, 판정은 `shared/index.ts` 의 `hasRole` 한 곳에서 합니다.
서버 라우트는 전부 `requireAccess(db, repoId, userId, 최소권한)` 을 거칩니다.

두 가지 규칙이 보안상 중요합니다.

1. **멤버가 아니면 404.** 403 을 주면 저장소 ID 를 넣어 보며 "존재하는 저장소"를 알아낼 수
   있습니다. 그래서 권한이 아예 없을 때는 존재 자체를 숨깁니다.
2. **열람 권한도 제안은 올릴 수 있다.** 이게 이 서비스의 기여 통로입니다. 대신 제안은
   `proposal_changes` 에만 쌓이고 `snapshots` 에는 손대지 않습니다.

멤버 이메일은 소유자에게만 보여 줍니다.

## 변경 제안과 병합

### 제안을 만들 때

1. 클라이언트가 파일을 `POST /repos/:id/blobs` 로 먼저 올립니다 → `blobs` 행만 생기고
   저장소 내용은 그대로입니다.
2. `POST /repos/:id/proposals` 에 `{path, blobHash}` 목록을 보냅니다.
   `blobHash: null` 은 삭제 제안입니다.
3. 서버가 **현재 head 를 기준으로 op 를 스스로 판정합니다.** 클라이언트가 보낸 op 는 믿지 않습니다.
   - 그 경로에 파일이 있으면 `update`, 없으면 `add`
   - 내용이 기존과 같으면 거부 (`내용이 그대로입니다`)
   - 없는 파일 삭제 제안도 거부
4. 이때의 head 를 `base_snapshot_id` 로 기록합니다. 나중에 충돌 판정의 기준이 됩니다.

### 충돌 판정

```
제안한 각 경로에 대해:
    base 의 해시 == head 의 해시  →  안전 (그 사이 아무도 안 건드림)
    head 의 해시 == 제안 해시     →  안전 (이미 같은 내용이 반영됨)
    그 외                         →  충돌
```

바꾸지 않은 파일이 head 에서 바뀐 것은 충돌이 아닙니다. **제안이 건드리는 경로만** 봅니다.

충돌이 있으면 `409` 와 함께 어떤 경로가 문제인지 돌려주고, 앱은 그 목록을 화면에 띄웁니다.
자동으로 합치지 않는 것은 의도한 것입니다 — 사진이나 문서 파일을 줄 단위로 합칠 수는 없고,
조용히 한쪽을 버리는 것보다 사람이 보고 정하는 편이 안전합니다.

### 병합

병합은 하나의 트랜잭션 안에서 head 를 **다시 읽고** 충돌을 다시 확인한 뒤 진행합니다.
두 명이 동시에 같은 제안을 병합하려 해도 한쪽만 성공합니다.

병합 결과는 새 스냅샷이므로, 병합 뒤에도 이전 상태를 그대로 볼 수 있습니다.

## 초대 코드

- 10자, `23456789ABCDEFGHJKMNPQRSTUVWXYZ` 알파벳 — `0/O`, `1/I/L` 처럼 헷갈리는 글자를 뺐습니다.
  전화로 불러 주거나 손으로 옮겨 적을 수 있어야 하기 때문입니다.
- 난수는 `crypto.randomBytes` 로 만들고, 모듈로 편향을 없애려 알파벳 크기의 배수를 넘는 바이트는 버립니다.
- 입력은 `parseInviteCode` 로 정규화합니다. 소문자·하이픈·공백을 넣어도 됩니다.
- 제한: 권한(viewer/editor), 만료 시각, 최대 사용 횟수, 회수.
  **소유자 권한은 초대로 줄 수 없습니다.**

### 동시성

마지막 한 자리를 여러 명이 동시에 쓰려는 경우를 막기 위해, 사용 횟수 증가를 조건부 UPDATE
한 문장으로 처리합니다.

```sql
UPDATE invites SET use_count = use_count + 1
 WHERE id = ? AND revoked_at IS NULL
   AND (expires_at IS NULL OR expires_at > ?)
   AND (max_uses IS NULL OR use_count < max_uses)
```

`changes === 0` 이면 이미 소진된 것이므로 참여를 거부합니다.

### 이미 멤버인 경우

**참여 가능 여부보다 멤버 여부를 먼저 봅니다.** 링크를 두 번 누른 사람이 다른 사람 자리를
빼앗으면 안 되기 때문입니다. 이미 멤버면 사용 횟수를 건드리지 않고 저장소 정보만 돌려줍니다.
(이 순서를 반대로 짰다가 테스트에서 잡힌 부분입니다.)

## 보안에서 신경 쓴 것

| 위협 | 대응 |
| --- | --- |
| 경로 탈출 (`../../etc/passwd`) | `normalizePath` 가 `.`/`..`/제어문자를 거부. 게다가 저장은 해시 경로라 사용자 경로가 파일 시스템에 닿지 않음 |
| 업로드 파일로 XSS | Content-Type 을 업로더 말이 아니라 **확장자 화이트리스트**로 결정. `nosniff` 헤더. SVG·HTML 은 inline 금지 |
| 비밀번호 | scrypt(N=16384, 비동기) + 랜덤 솔트, 파라미터를 해시 문자열에 함께 저장 |
| 토큰 위조 | HMAC-SHA256 서명, `timingSafeEqual` 비교 |
| 계정 존재 여부 노출 | 로그인 실패 메시지를 하나로 통일하고, 없는 계정도 더미 해시를 검증해 응답 시간을 맞춤 |
| 저장소 존재 여부 노출 | 비멤버에게 404 |
| 파일명에 개행/따옴표 | `Content-Disposition` 에 ASCII 대체명 + RFC 5987 `filename*` 동시 사용 |
| 대용량 업로드 | 스트리밍 중 바이트를 세다 한도를 넘으면 즉시 끊고 임시 파일 삭제. multipart 가 조용히 잘라낸 스트림(`truncated`)도 413 |
| 디스크 고갈 | 저장소 총량(`LISTUP_MAX_REPO_MB`)과 사용자별 하루 제안용 업로드(`LISTUP_MAX_STAGING_MB_PER_DAY`) 한도 |
| 남의 저장소 blob 참조 | 제안에는 그 저장소에 올렸거나 이력에 있는 blob 만 (`repo_blobs`) |
| 추방된 사람의 초대 | 발급자가 editor 이상 멤버가 아니면 초대 무효, 추방·강등 시 회수 |

## 앱 구조

```
app/
├─ app/                       expo-router 라우트
│  ├─ _layout.tsx             AuthProvider + Stack
│  ├─ index.tsx               저장된 토큰 확인 후 분기
│  ├─ login / signup / join / settings / repos
│  ├─ repo/[repoId]/          index(파일) · proposals · new-proposal · members · invites · history
│  └─ proposal/[proposalId]   제안 상세 · 리뷰 · 병합
└─ src/
   ├─ api/client.ts           타입이 붙은 API 래퍼, 401 시 자동 로그아웃
   ├─ state/auth.tsx          토큰 보관(AsyncStorage) 및 복구
   ├─ lib/files.ts            플랫폼별 파일 선택/저장
   ├─ lib/dialogs.ts          웹/네이티브 확인 대화상자
   ├─ components/             공용 UI + 저장소 탭 네비게이션
   └─ theme.ts                라이트/다크 팔레트
```

### 플랫폼 차이를 흡수하는 곳

파일 선택과 저장은 웹과 네이티브가 다릅니다. 그 차이를 `src/lib/files.ts` 한 곳에 모았습니다.

| | 웹 | 네이티브 |
| --- | --- | --- |
| 선택 | `File` 객체를 그대로 FormData 에 | `{uri, name, type}` 를 FormData 에 |
| 저장 | Blob → `URL.createObjectURL` → `<a download>` | 캐시에 내려받은 뒤 공유 시트 |

다운로드에 인증 토큰이 필요하므로 링크를 그냥 열 수 없고, 항상 헤더를 붙여 직접 받습니다.

### 서버 주소 결정

1. `EXPO_PUBLIC_LISTUP_API_URL`
2. `app.json` 의 `extra.listupApiUrl`
3. 개발 중이면 Expo 개발 서버의 호스트에서 유추 (실기기에서 `localhost` 는 기기 자신이므로)
